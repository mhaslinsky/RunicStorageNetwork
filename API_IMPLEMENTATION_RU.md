# API: реализация и локальная проверка

30 сентября 2026 года. Экспериментальный API версии **0.8.8**. Документ описывает реализацию и подтверждённые проверки этой версии.

## Что реализовано

В `RunicStorageNetwork.API.NetworkResources` добавлены три согласованных метода:

| Метод | Результат |
| --- | --- |
| `GetResources` | Неизменяемый снимок доступных ресурсов, состояние сети, полнота и сведения о последней оплате потребителя. |
| `GetResourceAmount` | Количество конкретного prefab и качества. При неполных данных точное количество остаётся неизвестным, а не превращается в ноль. |
| `TryConsumeResources` | Асинхронная оплата одного ресурса или набора с результатом `Success`, `NoDebit` либо `OutcomeUnknown`. Сам предмет машине не создаётся. |

API доступен только поверх включённого эксперимента удалённых сетей. Потребитель — неподвижная постройка игрока с `Piece`, `ZNetView` и маркером `NetworkConsumer`. Новые запросы делает текущий владелец постройки; доступ проверяется по создателю и оберегам. Работают ванильные и подходящие модовые контейнеры через действующие правила допустимости. Отдельного списка разрешённых категорий предметов нет.

Чтение использует общий кеш по сети и правам, компактные снимки инвентарей и существующий обратный индекс ресурсов. Фоновая работа ведётся только для недавно запрошенных сетей. Сундуки при чтении не резервируются и вся область мира не загружается.

Списание выполняет сервер после получения свежего содержимого от владельцев выбранных сундуков. Используются общие с крафтом игроков блокировки. Дельты всех источников подготавливаются до первой записи. При частичном сбое возвращаются только ресурсы этой операции. Старые пакеты от прежнего владельца не могут перезаписать защищённый сундук, даже если у них выше версия содержимого.

До списания система сама обновляет привязку сети, права и количества, исключает отказавший источник из текущего плана и пробует перепланировать оплату. Есть ограниченное окно старта и четыре восстановительных прохода. После первой записи сохраняется тот же запрос до завершения или компенсации — новая оплата вместо неопределённой не запускается.

На потребителя хранится один последний запрос и результат с монотонным номером. Повтор идентичного запроса возвращает прежнюю операцию. Изменение состава под тем же номером отклоняется. Новые запросы ограничены по частоте, количеству источников и памяти; за API закреплено не больше 64 из общих 256 мест операций, поэтому оно не может занять более четверти этих мест. Очередь повторных подтверждений отделена от очереди чтений.

При выключенном эксперименте на старте API-компонент и его дополнительные патчи не устанавливаются. В обычном транспорте оставлены только необязательные делегаты для общих блокировок и подсчёта операций; без API они пустые. Имена API-операций не попадают в старые неограниченные истории обычного крафта.

## Собрано

- `dist/RunicStorageNetwork-0.8.8.zip` — основной мод с API, шесть утверждённых файлов пакета.
- `dist/RunicStorageNetwork-ApiTest-0.1.0.zip` — отдельный тестовый плагин и инструкция.
- [API.md](API.md) — контракт и примеры для разработчиков на английском.
- [Исходник тестового мода](examples/ApiTestMod/ApiTestMod.cs) использует только публичный API. В основной пакет он не включён.

Сборщик `tools/BuildApiPreview.ps1 -Release` компилирует обе DLL, запускает изолированные тесты, проверяет структуру установленного сетевого протокола по метаданным игровой DLL и содержимое основного архива. Игровые библиотеки в архивы не включаются. Для визуальных ресурсов используется утверждённый ранее пакет; Unity-проект не пересобирается.

## Что проверено автоматически

Проходят **478 проверок**: 243 проверки чистой логики и 235 проверок производственных методов с подставными игровыми объектами. Из них 50 новых проверок непосредственно относятся к API.

Проверены нормализация запроса, точное качество, неизменяемые DTO, частичный нулевой остаток, повтор и конфликт запроса, смена владельца при повторе, пределы истории/очередей, автоматическое исправление устаревшего состояния, отсутствие списания до подготовки всех источников, возврат после ошибки сохранения, повтор восстановления, очистка после успеха и общий резерв с игроком.

Отдельный набор компилирует производственный `ApiOwnership.cs`: проверяет чужие и поздние пакеты, более новую версию содержимого от старого владельца, сохранение посторонних записей пакета, неполный пакет, повтор подготовки, получение содержимого порциями, блокировку до подтверждённого освобождения и переполнение версии владельца. Последняя оплата не удерживает ссылки на освобождённые инвентари.

Это **изолированные автоматические проверки**, а не запуск Valheim. Дополнительно автор проверил API в одиночной игре рядом с ядром и вне его области загрузки: списание железных гвоздей в разных количествах прошло успешно. В просмотренных логах есть подтверждения оплаты 1 и 5 гвоздей без ошибок API. Полноценная проверка API между несколькими клиентами ещё не выполнена.

## Как проверить локально

Тестовый потребитель намеренно работает только в одиночном мире: это небольшой пример с авторитетным локальным буфером, а не готовая сетевая машина для чужого мода. Серверно-клиентская часть самого API реализована отдельно и требует последующего мультиплеерного испытания.

1. Установить основной пакет 0.8.8 в отдельный тестовый профиль. Папку `plugins/RSN.ApiTest` из второго архива разместить в `BepInEx/plugins` этого профиля.
2. В конфиге RSN включить `ExperimentalUnloadedNetworks = true` и полностью перезапустить игру.
3. Построить **API Test Consumer** молотком в категории Crafting рядом с ядром или подключённым реле. Постройка выглядит как верстак, цена — одна древесина. Команды выбирают ближайший такой объект в пределах восьми метров.
4. Положить древесину в подключённый сундук. В консоли выполнить:

```text
rsn_api_test list
rsn_api_test amount Wood
rsn_api_test pay Wood 5
rsn_api_test status
rsn_api_test retry
```

Первый запрос может вернуть `Updating`: повторить через секунду. При оплате из сундуков должно уйти ровно пять древесины, а в `status` появиться пять оплаченных единиц. Повторять `retry` можно много раз — древесина и счётчик больше меняться не должны.

**Материалы списываются по-настоящему в тестовый счётчик.** Новые предметы не выдаются, при разборке тестового верстака накопленные единицы не возвращаются. Использовать отдельный тестовый мир.

Дальше проверить разложенные по нескольким сундукам материалы, добавление недостающего ресурса после отказа, временно разорванную связь реле, удалённый сундук без посещения ядра, занятый сундук, возможность открыть и разобрать сундук после завершения. При выключенном эксперименте и полном перезапуске API должен вернуть `FeatureDisabled` без списания.

## Границы первой сборки

- Потребитель обязан хранить запрос и авторитетный оплаченный буфер. Сам API не может сделать произвольный callback чужого мода однократной выдачей предмета. В примере используются состояния `Pending → Paid → Applied`, а после `NoDebit` — автоматическое ожидание сети/ресурсов и новый номер той же производственной задачи.
- Квитанции живут в рамках сеанса сервера. После аварии или перезапуска с неопределённой оплатой возвращается `OutcomeUnknown`; автоматическая повторная выдача запрещена. Пример сохраняет такой случай как `RecoveryRequired`.
- Снятие только конкретного уникального экземпляра с особыми метаданными не входит в контракт: требуется явное согласие `AnyMatchingInstance`.
- Кооперативный обход ограничен по времени, но отдельная десериализация инвентаря, построение графа и вызов стороннего обработчика остаются неделимыми операциями. Предельную нагрузку нужно измерить на реальной большой базе.
- Пакетная защита проверена по формату текущей установленной игры. После изменения сетевого формата Valheim её необходимо пересмотреть.
- Для дальнейшего тестирования экспериментального API остаются живые проверки двух клиентов: одновременный крафт/оплата, открытый модовый сундук, отключение владельца на разных стадиях, смена владельца потребителя и восстановление результата без повторной выдачи. Маленький одиночный тестовый мод этих проверок не заменяет.
