# Runic Gateway — реализация для локальной проверки

Ветка: `feature/runic-gateway`. Версия пакета: `0.9.0-gateway-preview` (в manifest и DLL — `0.9.0`). Публикация на площадках в эту работу не входит.

## Постройка

- **Runic Gateway / Рунический мост**, внутренний prefab `RSN_RunicGateway`.
- Молот, категория Crafting, рядом с обычным верстаком. Открытие по знакомству с ингредиентами.
- Камень ×20, древесина Иггдрасиля ×10, серебро ×6, кристалл ×10, очищенный эйтр ×5.
- Утверждённый вид v14 с обычным камнем, прежними прорезанными рунами, древесиной и металлическими деталями. Normal map камня — 0.40, древесины — 0.28. Игровые материалы назначаются из установленного Valheim.
- Иконка с направленным освещением; эффекты установки, попадания и разрушения взяты у `stone_floor`.
- 9 069 треугольников, 10 рендереров, 6 коллайдеров. Воздушный зазор возле кристалла сохранён. Нижний коллайдер служит опорой при размещении молотком.
- Рабочая парная связь включает полное свечение. Без неё кристалл, руны и каналы тускнеют. При наведении показываются имя связи и состояние; E открывает штатный ввод текста в общем стиле интерфейса мода.

## Включение и привязка

Используется существующая настройка в `BepInEx/config/local.runicstoragenetwork.cfg`:

```ini
[Experimental]
ExperimentalUnloadedNetworks = true
```

Настройка по умолчанию выключена. Для мультиплеера она нужна на сервере и у всех клиентов с одинаковой версией мода; после изменения требуется полный перезапуск. При выключенной функции мост остаётся видимой постройкой, но не образует дальнюю связь и не работает локальным реле.

1. Поставить первый мост в связанной с ядром части сети и задать имя связи.
2. Поставить второй мост на удалённой базе и ввести то же имя.
3. Продолжить сеть обычными реле либо использовать снабжение самого моста.

Сравнение имён учитывает регистр. Поле нормализуется существующим `NetworkLabels`, предел — 40 символов. Ровно два моста с одинаковым непустым именем составляют пару. Три и более отключают дальнюю связь всех мостов с этим именем. Наличие третьего учитывается и за пределами загрузки, и за чужой защитой.

Привязка хранится в существующем ZDO моста (`rsn_gateway_network`), имя связи — `rsn_gateway_tag`. Используется сохранённая идентичность ядра, которая переживает смену runtime ZDOID после загрузки мира. Привязка назначается сервером после ввода непустого имени. Неназванный второй мост не получает постоянную привязку к случайному соседнему ядру: после задания имени он может унаследовать сеть первого моста.

Уже привязанный мост не переключается на чужую сеть при переименовании. Для смены ядра нужно разобрать и поставить его заново. Два независимо привязанных моста не объединяют свои сети. Если рядом с удалённым мостом есть чужое ядро, его локальные связи отсекаются; эта чужая сеть остаётся отдельной. Обычное объединение локальных Core/Relay между собой сохраняется.

## Граф и производительность

`GatewayGraph` расширяет существующий `NetworkGraph`: обычные связи строятся по расстоянию, паре мостов добавляется одно двустороннее ребро без ограничения длины. Сами мосты используют `RelayLinkRange`, `RelayStorageRadius` и `RelaySupplyRadius`. Бесконечного локального радиуса нет.

Для каждого снимка топологии один раз определяются обычные связные компоненты **без дальних рёбер**. Для пары «источник — потребитель» сохраняется один из трёх результатов: пути нет, есть обычный путь, нужен мост. При наличии обычного обходного пути он имеет приоритет для ограниченных ресурсов, даже если мост короче.

Граф кэшируется по миру, ревизии каталога и правам игрока; результат маршрута — по сети и позициям источника/потребителя. Новый предмет или новое количество в сундуке не вызывают перестроение графа. Кэш обновляется при изменении структуры, имён, привязок, защиты, настроек или мира. Перемещение потребителя создаёт другой ключ маршрута. Размеры кэшей ограничены: 128 снимков по игрокам, 128 позиций покрытия и 16 384 результата маршрутов на снимок.

На кадре интерфейса не запускается полный поиск пути для каждого предмета. Первая проверка пары позиций на новом снимке проверяет покрытие, последующие читают кэш. Проверка перед результатом крафта/выдачи тоже использует этот кэш и не повторяет полный разбор рецепта и станции. Граф создаётся синхронно при изменении ревизии: время первого обращения на очень большом мире и реальные FPS ещё нужно измерить в игре.

Циклы и несколько пар поддерживаются; сундуки учитываются по существующим стабильным ключам без дублирования. Новый предмет Builder’s Codex не добавлялся: обычное строительство и будущие потребители используют покрытие локального узла, включая мост, а не прямую связь с ядром через весь мир.

## Какие ресурсы доступны

Применяется ванильное правило обычного портала из `Inventory.IsTeleportable(false)`: `ItemDrop.SharedData.m_teleportable`, мировой модификатор `TeleportAll` и абсолютное ограничение `m_toolTier >= 1000`. Списка названий или категорий предметов нет. Неизвестный prefab не допускается через дальнюю связь.

Ограничение применяется только к маршруту через мост:

| Источник и путь | Дерево | Железо при обычных правилах порталов |
|---|---|---|
| Сундук рядом с потребителем, обычная часть сети | Доступно | Доступно |
| Сундук за дальним мостом | Доступно | Недоступно |
| Между сторонами также есть обычная цепочка реле | Доступно | Доступно |

Общий индекс сундука хранит исходный запас. Фильтрация создаёт представление для конкретного потребителя и не заменяет общие остатки: игрок по другую сторону моста получает свой правильный список. Крафт проверяет точку станка, строительство — игрока, выдача через Кодекс запасов — постамент, API — зарегистрированное устройство. Изменение мирового правила порталов не требует перестройки геометрии графа.

Фильтр подключён к отображению/подбору ресурсов, свежему плану списания координатора, выдаче результата и API. Обычные проверки доступа, владельца сундука, резервирования и актуальных остатков остаются в существующей транзакции. Изменение пути во время операции приводит к её существующему механизму отмены/возврата/восстановления, а не выдаче запрещённых материалов. Это не гарантия завершения после аварийного завершения процесса: прежние ограничения транзакций при падении игры сохраняются.

Моды, которые переопределяют поведение порталов отдельными Harmony-патчами или меняют свойства только отдельных экземпляров предметов, не покрываются автоматически одним prefab-свойством; такие сочетания требуют отдельной проверки.

## Непрогруженные области и мультиплеер

Мост включён в существующий каталог сохранённых узлов `UnloadedNetworks`. Отдельных инвентарей или копий мира нет. При обращении используются записи сети и прежние лёгкие адаптеры, а не принудительная симуляция всей области.

Сервер определяет принадлежность и выполняет существующий протокол списания. Для одинаковой топологии клиентам дополнительно передаются записи узлов и влияющих на них защитных камней, даже если удалённый мост сейчас не даёт доступа к ядру. Это позволяет увидеть третью одноимённую точку, чужое ядро и разрыв связи. Содержимое посторонних сундуков в такой каталог не добавляется. Передача остаётся в существующих ограниченных страницах и покадровых бюджетах; предел протокола — 65 536 записей.

Состояние моста сохраняется в обычных ZDO. Закрытый сундук не резервируется из-за самого факта существования моста. Списание/выдача используют прежние кратковременные резервы и защиту от повторной оплаты. Сценарий холодного входа рядом со вторым мостом должен работать через существующее обнаружение по обращению; реальную доставку ZDO/RPC на двух клиентах надо подтвердить вручную.

## Проверено автоматически

- DLL собирается по установленным игровым библиотекам. Локальная проверка сигнатур/IL игрового API прошла; это не запуск Harmony в игре.
- **513 тестов прошли**: 264 изолированных; 26 строительства; 36 рецептов; 27 инспекции; 22 индекса хранилищ; 13 подготовки; 29 выдачи через терминал; 69 непрогруженных сетей; 15 владения API; 12 Gateway runtime. Runtime-наборы используют подставные игровые классы.
- Новые сценарии: удалённая пара, местное/дальнее железо, обычный обход, несколько пар и циклы, удаление ядра/реле/моста, смена имени, третья точка, конфликт сетей, новая runtime-идентичность мира, второй мост рядом с чужим ядром, клиентский каталог без доступного ядра.
- 10 000 обращений используют один результат маршрута. 2 000 изменений ревизии инвентаря не меняют объект кэшированного графа. Проверено отключение экспериментальной ветки и актуальное мировое правило порталов.
- Unity **6000.0.75f1**, Editor без Play Mode: полная сборка и повторная загрузка Windows AssetBundle; все пять prefab и пять иконок доступны; геометрия, UV, шейдеры, шесть коллайдеров и 13 проверок размещения/зазора прошли. В пакет не входят игровые DLL и исходные игровые материалы.
- В ZIP ровно шесть файлов: DLL, AssetBundle, manifest, icon, README и английский CHANGELOG. Ветка и пакет предназначены для локального теста.

Логи: `artifacts/gateway/final-tests.log`, `artifacts/gateway-20261001-154728/UnityEditor.log`, `artifacts/gateway-20261001-154728/API_CHECK.txt`. Последняя компиляция DLL: `artifacts/gateway/final-bin`.

## Ручная проверка

- [ ] Включить функцию, перезапустить игру; поставить мост молотом. Проверить открытие рецепта, материалы, звук, удаление и возврат ровно одного комплекта материалов.
- [ ] Назвать первый мост у ядра, второй вдали — так же. Проверить статус и усиление свечения.
- [ ] Продолжить дальнюю сторону реле: покрытие и радиусы обычные, вдали от локальных узлов доступа нет.
- [ ] На основной базе положить дерево и железо, на удалённой — другое количество железа. Сравнить числа и крафт на обеих сторонах.
- [ ] Повторить проверку через Кодекс запасов, строительство и тестовый потребитель API.
- [ ] Добавить обычную цепочку реле между сторонами: железо основной базы становится доступно. Разорвать эту цепочку: остаётся только местное железо.
- [ ] Разорвать реле перед первым мостом, затем восстановить: удалённая сеть отключается и возвращается без переименования.
- [ ] Разрушить мост, восстановить с прежним именем: связь возвращается. Проверить отсутствие повторной выдачи строительных материалов.
- [ ] Переименовать одну сторону, затем вторую: связь исчезает и появляется. Пустое имя отключает дальнюю пару.
- [ ] Добавить третий мост с тем же именем, включая выгруженный: пара отключается; дать третьему другое имя — восстанавливается.
- [ ] Попробовать соединить два уже привязанных моста независимых сетей: сети не объединяются.
- [ ] Сначала назвать мост у ядра A; затем поставить неназванный мост рядом с ядром B и дать ему имя первого. Он продолжает A, не объединяя A и B.
- [ ] Две разные пары, последовательные мосты и замкнутый путь: ресурсы не удваиваются.
- [ ] Включить защиту и изменить разрешения во время открытого окна: запрещённые пути/источники недоступны.
- [ ] Зайти после сохранения сразу у удалённого моста, не посещая ядро. Открыть Кодекс, дождаться обнаружения, забрать ресурс.
- [ ] Два игрока на разных концах, отдельный сервер: параллельный крафт и выдача; один сундук открыт другим игроком; после закрытия доступ восстанавливается.
- [ ] Во время операции разорвать связь или изменить имя: нет бесплатного результата/двойного списания; после возврата связи запрос работает.
- [ ] Изменить мировое правило переноса металлов: дальнее железо соответствует этому правилу, местное всегда доступно.
- [ ] Сохранить/перезагрузить мир: имена и привязки сохраняются, включая две физически соединённые обычные сети с несколькими ядрами.
- [ ] Выключить функцию у всех и перезапустить: мосты не снабжают, обычные Core/Relay и инвентари работают как прежде.
- [ ] На большой базе сравнить FPS и время первого/повторного открытия станка и Кодекса. Отдельно проверить модовые хранилища.
